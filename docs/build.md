# Building for ReactOS

A cross-compile from Linux with `i686-w64-mingw32`. **Verified working** — the
recipe below was executed and produced a 32-bit `echoserver.exe`.

It is *not* a turnkey upstream path: wolfSSH's examples are POSIX-oriented and
the library needs two small workarounds. This file records exactly what works
and why each workaround exists, so the knowledge does not have to be rediscovered.

## Sources

Both libraries are pinned git submodules under `third_party/` — the exact
revisions this project builds and ships against, which is also what GPLv3
compliance requires.

```sh
git clone --recurse-submodules <repo-url>      # or, in an existing clone:
git submodule update --init --depth 1
```

| Submodule | Revision | Tag |
| --------- | -------- | --- |
| `third_party/wolfssl` | `ac01707` | `v5.9.2-stable` |
| `third_party/wolfssh` | `8643d7b` | `v1.5.0-stable` |

A git checkout carries `configure.ac` but **no `configure`** — that has to be
generated once, which is step 1.

## Versions used

| Component | Version | Note |

## Step 1 — generate `configure`

```sh
( cd third_party/wolfssl && ./autogen.sh )
( cd third_party/wolfssh && ./autogen.sh )
```

Both exit 0 and leave a `configure` behind (1.4 MB and 700 KB). The generated
files are ignored by each submodule's own `.gitignore`, so the pinned trees stay
clean.

If you would rather not depend on autotools, the release archives already contain
a generated `configure` — that is how the spike was first run. They are served
from the site root, without the `-stable` suffix the tags carry, and **not** from
`/download/`:

```sh
curl -O https://www.wolfssl.com/wolfssl-5.9.2.zip     # 29.8 MB
curl -O https://www.wolfssl.com/wolfssh-1.5.0.zip     #  1.2 MB
```

## Step 2 — wolfSSL

```sh
cd third_party/wolfssl
./configure --host=i686-w64-mingw32 \
  --prefix=/tmp/rosssh-spike/prefix \
  --enable-wolfssh --enable-curve25519 --enable-ed25519 --enable-aesgcm \
  --enable-static --disable-shared \
  --disable-examples --disable-crypttests \
  --disable-mlkem --disable-pqc-hybrids
make -j8 && make install
```

## Step 3 — the include shim

```sh
mkdir -p /tmp/rosssh-spike/shim
printf '#include <ws2tcpip.h>\n' > /tmp/rosssh-spike/shim/WS2tcpip.h
```

## Step 4 — wolfSSH

```sh
cd third_party/wolfssh
./configure --host=i686-w64-mingw32 \
  --prefix=/tmp/rosssh-spike/prefix \
  --with-wolfssl=/tmp/rosssh-spike/prefix \
  --enable-sftp --enable-static --disable-shared \
  CPPFLAGS="-I/tmp/rosssh-spike/shim" \
  CFLAGS="-g -O2 -Wno-error=incompatible-pointer-types"

# the library and the server example; the client examples do not build (see below)
make examples/echoserver/echoserver.exe
```

`make` on its own fails — but only in `examples/client` and `examples/scpclient`.
Building the target explicitly is the way through.

## Workarounds, each for a concrete upstream problem

1. **ML-KEM vs. version skew.** `src/internal.c` includes
   `<wolfssl/wolfcrypt/mlkem.h>` under `#ifdef WOLFSSL_HAVE_MLKEM`, but wolfSSL
   5.9.2 no longer ships that header (it has `wc_mlkem.h`) → fatal error. The
   clean fix for us is to build wolfSSL with `--disable-mlkem
   --disable-pqc-hybrids`: we do not want post-quantum hybrid KEX on ReactOS
   anyway, and it keeps the crypto surface smaller. The alternative is pinning an
   older wolfSSL that still carries `mlkem.h`.
2. **`<WS2tcpip.h>` — capitalisation.** The Windows branch of wolfSSH's examples
   includes the header with a capital `W`. mingw-w64 ships it as `ws2tcpip.h`,
   and the cross-compile host's filesystem is case-sensitive. The shim directory
   in step 2 resolves it without patching upstream.
3. **GCC 14 makes `-Wincompatible-pointer-types` an error.** `src/wolfsftp.c`
   passes an `int *` where `ReadFile` wants a `DWORD *`. `-Wno-error=` demotes
   that one diagnostic without disabling `-Werror` globally.
4. **SCP does not build for mingw.** `--enable-scp` compiles `src/wolfscp.c`,
   which uses `_SH_DENYNO` — an MSVC `_sopen_s` sharing flag that mingw does not
   provide. Consequence: legacy `scp -O` would need a patch. Modern `scp` speaks
   **SFTP**, which is enabled here, so the transfer goal is still met.
5. **The client examples are POSIX-only.** `examples/client` needs `pthread`,
   `ioctl`, `TIOCGWINSZ`, `SIGWINCH`; `examples/scpclient` needs `termios.h`.
   Neither is portable to mingw. `examples/echoserver` builds fine.

## Verified result

```
examples/echoserver/echoserver.exe: PE32 executable for MS Windows 4.00 (console), Intel i386
src/.libs/libwolfssh.a                                       1,024,866 bytes
```

| Property | Value | Why it matters |
| -------- | ----- | -------------- |
| Subsystem version | **4.0 (NT4)** | older than wSSH's 5.0 — no loader version risk at all, unlike Win32-OpenSSH's 6.0 |
| Imported DLLs | `ADVAPI32`, `CRYPT32`, `KERNEL32`, `msvcrt`, `WS2_32` | all ancient and all present in ReactOS |
| UCRT / `vcruntime` | absent | no redistributable to ship |
| `bcrypt` | absent | the engine is statically linked |
| Notable modern import | `CryptGenRandom` | **this is the weak ReactOS RNG** — it must be replaced by our own pool ([reactos.md](reactos.md) §2, [../spec.md](../spec.md) §6.1) |

## Open items

- The full cross-build was verified from the release archives. The submodule
  path was verified as far as `autogen.sh` + a generated `configure`; a full
  submodule-based cross-build runs as part of M1.
- The spike linked the *upstream example*. Our own server is not written yet.
- `wolfSSHd`, wolfSSH's own Windows server, is deliberately not used: its Windows
  authentication goes through the token stack (`SetupUserTokenWin`), which is
  exactly what we avoid on ReactOS ([../spec.md](../spec.md) §4.2).
- Whether the *static* wolfSSL RNG path can be redirected cleanly
  (`CUSTOM_RAND_GENERATE_BLOCK` / `wc_SetSeed_Cb`) is not yet verified — it is
  the first task of M1.
